The first version of an AI budget usually lives in the billing console.

That is useful until a user reaches the limit and the product changes behavior without warning. A model disappears. A batch pauses halfway through. A long document refuses to process. The user experiences the billing policy as a product failure because the interface never explained the transition.

A cap is a state machine whether the team calls it one or not.

At 90 percent, perhaps the product warns an admin. At 100 percent, background jobs pause while short interactive requests use a cheaper route. Above the hard limit, high-cost work requires explicit approval. Different products will choose different states. The important part is that the user can tell which state they are in and what happens next.

There are several ways to degrade:

- use a smaller model
- reduce context
- skip expensive reranking
- process fewer files
- delay background work
- ask the user to narrow the request
- require approval

Those options are not interchangeable. A cheap summary can move to a smaller model. A security-sensitive classifier probably should not silently do so. Reducing context for brainstorming is different from reducing context for contract review.

The interface should name the downgrade:

~~~text
Using the low-cost path for this request.
Large-file analysis is paused until the project budget resets.
~~~

Rough estimates are useful even when exact prediction is impossible:

~~~text
expected cost: about $0.40 to $0.70
reason: 183 pages, OCR enabled, long-context model selected
budget impact: 7 percent of today's project limit
~~~

That gives the user a lever. They can upload cleaner files, choose a smaller model, split the document, or ask for approval. A meter without a cause teaches nobody anything.

Budget events should leave a trail too. Record which project reached its limit, which jobs paused, which fallback route stayed available, and which requests needed approval. Cost is operational state. It belongs beside the run, not in a separate export nobody checks until the invoice arrives.

I would test caps with small staging budgets. Hit warning, degraded, blocked, approval-required, and resume states before a real customer does. The expensive path should be boring before it becomes expensive.
