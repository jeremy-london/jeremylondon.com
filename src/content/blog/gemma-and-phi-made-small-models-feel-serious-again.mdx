[Gemma](https://blog.google/innovation-and-ai/technology/developers-tools/gemma-open-models/) and [Phi-3](https://news.microsoft.com/source/features/ai/the-phi-3-small-language-models-with-big-potential/) made small models feel like architecture again.

The useful change was not magic. It was placement. A small model can be a local classifier, preprocessor, first pass, narrow router, or verifier with a limited blast radius while a larger model handles ambiguity.

A local secret-scanning route makes the boundary clear:

~~~python
result = model.predict_entities(
    text=note,
    labels=["api_key", "token", "password", "private_key"],
    threshold=0.35,
)

if result.confidence < 0.7:
    route = "review"
else:
    route = "redact"
~~~

The model owns one job and has an escape hatch. The same pattern works for document intake, obvious redaction, queue routing, and other steps where a local decision is cheaper or more private than a general model call.

Write the route down:

~~~text
input: local note under 20 KB
labels: api_key, token, password, private_key
threshold: 0.35
fallback: deterministic scan + human review
route: local first
~~~

That record makes the model's role legible. It is not a general assistant. It is a bounded component with a defined failure path.

Open weights also change the debugging loop. Teams can measure memory, quantize the model, test local hardware, and observe the real deployment cost rather than guessing from an API demo.

Gemma and Phi were a reminder that size is not the identity of a model. Placement, scope, and escalation path matter just as much.
