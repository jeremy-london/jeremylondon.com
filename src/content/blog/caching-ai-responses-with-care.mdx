Caching makes an AI product feel faster almost immediately. Repeated questions stop consuming tokens, latency drops, and the bill looks better.

The hidden cost is confidence. A stale answer still arrives in the same polished voice as a fresh one.

An AI cache stores more than a string. It stores an answer produced under a particular model, prompt version, retrieval state, policy, user scope, and output contract. If those conditions change, the hit may be invalid even when the prompt is identical.

A prompt-only key is usually too optimistic. For a private workflow, I want the key or entry metadata to account for things like:

- model and prompt-template versions
- tenant and user scope
- retrieved source IDs or hashes
- retrieval-index version
- policy and output-schema versions
- tool-result versions

That list will differ for a public FAQ bot. The useful question is simpler: what conditions made this response reusable, and can the system prove that they still hold?

Freshness also comes from source state, not only time. A document update, permission change, rebuilt index, retired model, or changed policy can invalidate an answer before its TTL expires. A short TTL is helpful, but it cannot notice every event that changes meaning.

Private data raises the bar. A response generated for one user should not become available to another because their prompts happen to match. Workspace-level and tenant-level caches are only safe when they match the actual permission boundary of the retrieved material. Store enough scope information to answer who the entry was safe for and whether that remains true.

I usually look for cheaper, more deterministic cache layers first:

- OCR output keyed by file hash
- parsed document structure
- tool results with source timestamps
- embeddings for unchanged chunks
- retrieval results with permission metadata

A model response is more interpretive. It can still be cached, but it deserves stronger validation because it may hide stale inputs behind fluent prose.

Every hit should be explainable. A useful receipt might include:

~~~text
created_at: 2026-07-13T15:18:09Z
model: reasoning-small-2026-06
prompt_version: incident-summary-v4
source_hashes: doc_123:8ac1, doc_456:91fb
permission_version: workspace_77:44
invalidates_on: source_hash_change, permission_change, prompt_change
~~~

For private data, the receipt should make the permission boundary explicit too:

~~~json
{
  "scope": {
    "tenantId": "t_123",
    "resourceIds": ["doc_7", "doc_9"],
    "permissionVersion": "workspace_77:44"
  },
  "generatedBy": {
    "model": "reasoning-small-2026-06",
    "promptVersion": "incident-summary-v4"
  }
}
~~~

When a user reports a wrong answer, "cache hit" is not an explanation. The system should be able to say what matched and which freshness checks passed.

Some products should expose that state in the interface:

~~~text
Generated 12 minutes ago from the current document version.
~~~

That line is useful for operational summaries and analysis. It gives the user a basis for deciding whether the result is current enough to act on.

The safest cache policy is still selective. Cache public documentation, parsed files, low-risk suggestions, and versioned evaluation fixtures. Be much more cautious with account access, billing, security decisions, health or legal guidance, and actions that execute without review.

A fast answer is not automatically a useful answer. The cache has to respect model version, source state, permissions, policy, schema, and the cost of being wrong.
